    01

    Purpose

    Transform the product from an issue-logging tool into an inspection and report-generation workflow for field inspectors.

    The usage phase must let inspectors start an inspection on site, capture evidence and findings, use AI assistance, review outputs, sign off, and publish a report from mobile or desktop.

    02

    Goals

    • Let inspectors start an inspection directly on site without office scheduling.
    • Support quick manual entry for structured data and AI assistance for narrative content.
    • Preserve inspector control through review, editing, and conflict handling before publication.
    • Generate reports from inspection data using either customer-specific or default templates.
    • Make inspections and reports accessible on both mobile and desktop.

    User Primary needs

    Inspector returning from site Use AI once internet is available to expand narrative fields and incorporate document references
    Manager View team inspections and reports

    Inspection lifecycle

    6.1Terminology

    Rename Journal to Inspections throughout the product.

    Partial  Tab = Inspections; legacy strings and API identifiers remain.

    6.2Statuses

    Status Target definition Current behavior
    Scheduled Future-dated inspection with no entered data Empty inspection or “start from scratch.” scheduledAt field exists but is not set — future-date scheduling is not implemented
    In Progress Data entry has started Set when checklist is selected, content exists, or first answer entered
    Completed Report published for the inspection Also triggered when walk is archived or all publishable issues are published to workspace — may diverge from “report file exported”

    6.3Report status (secondary axis)

    Separate from lifecycle, report status currently intrinsically indicates:

    Report status Meaning
    Not published No export or workspace publish
    Pending Publish in progress
    Published Report file exists and/or items published to workspace
    Current stateComputed client-side (published | pending | not_published) but not displayed on inspection list cards. May decide to display in the future.

    6.4Inspection list journey

    1. Inspector opens Inspections tab.
    2. Filters by Scheduled / In progress / Completed.
    3. Card shows checklist name; report template name is modeled but often shows “No report template” because export choice is not persisted to inspection metadata after export.
    4. Swipe archive toggles lifecycle locally (optimistic).

    An inspection started directly on site appears as In Progress once the inspector begins entering data.

    Core onsite workflow

    7.1Start inspection

    Inspectors must be able to begin without an office user creating or scheduling the record first.

    Target flow

    Open Inspections → start new → select project → select checklist → complete forms & findings → review & publish report.

    Implemented create paths

    Path Steps Result
    Online create Implemented Inspections (+) → Choose project → Pick team checklist Walk created with one issue per requirement; lifecycle In Progress
    Start from scratch Hidden from UI Skip checklist at create Scheduled empty inspection with one blank issue
    Offline create Not possible this release Skip project/checklist when offline Bare walk without project/checklist — not possible in this release, since the checklist must load when there is signal

    Additional constraints

    • Solution Library checklists: adopt on web first; mobile lists team-adopted checklists only.
    • Multi-device (mobile + desktop): second device lazy-loads checklist schema; form answers autosave after 1 second when online; desktop visibility should sync. However, team visibility of in-progress inspection work is only available when published.

    8.2Manual-first use

    Inspectors must be able to manually complete fields while on site, including offline. Discrete fields (compliant/non-compliant, yes/no) are especially important offline.

    Form capture loop Implemented — assuming single inspector

    1. Inspector navigates issue carousel (each item = one checklist requirement instance).
    2. Forms render inside the item via requirement journal block.
    3. Answers stored locally: formAnswers[walkId][issueId][fieldId].
    4. When online: 1s debounced autosave; on reconnect, batch sync flushes pending issues.
    5. Conflict model today: server answers replace local wholesale on fetch — no field-level merge.
    Multiple inspectors — possibly not in this release Not developed yet. The UI needs to support showing offline captures from multiple inspectors once synced online. The Host has the right to confirm the final value for the report — choosing one value or all values to be shown. (JSON will need author name and timestamp at form-field level.)

    8.3Form usability — continuously improved

    Validate improvements for long forms and large option sets:

    • Stronger visual indication of selected binary or multiple-choice responses (color codes).
    • Alternative layouts for long multiple-choice lists.
    • Clear visibility of complete vs incomplete fields (required flags, completion checks, publish tag derivation).

    No hard limit on option count; long forms may use multiple forms or sections. UI or cosmetic improvements on form usability will be a work in progress — do not expect perfect polish in this release.

    09

    Findings and repeated items

    9.1Findings structure

    Data model: Findings are not a separate entity. They are form fields on checklist items (e.g. Compliant?, Finding category, Evidence, Action, Photo in the food-safety demo).

    A finding record may include: Location · Compliance status · Short defect / non-compliance description or relevant clause · Comment · Action required · Photos.

    9.2Duplicate and insertion behavior

    Action Behavior (current)
    Duplicate current item Copies requirement structure only (and carries over requirement ID in the JSON output); form values and inspector notes not copied
    Insert position Immediately after focused item (createdAt ordering); later items shifted
    Add blank item New issue without requirements, blank for notes capture; appears in content[] in the JSON
    Final section / sign-off placement Final checklist section(s) always remain last in carousel after any insert or duplicate — unless the final item itself is duplicated, in which case the duplicate appears immediately after it

    Sign-off is implemented as signature fields on designated final checklist section(s), not a dedicated sign-off route.

    9.3Checklist creation and on-site usage

    • Long checklists pre-create one carousel item per requirement at start.
    • Inspector duplicates an item when the same checklist section applies again on site.
    • Newly added or duplicated findings must remain before the final sign-off section.
    • JSON output will contain the duplicated items with identical requirement ID for looping.
    10

    AI assistance: Magic Wand

    10.1Purpose

    Hybrid workflow: offline capture on site, then AI drafts or improves narrative content after connectivity returns.

    10.2Modes

    Mode Requirement Current implementation
    Item-level Run Magic Wand for one finding or form item POST /form-fields/requirement — may modify existing values
    Batch Run across multiple items in parallel POST /form-fields/requirement/batch — may modify existing values; skips rows without journal notes; max 100 requirements per AI API call, but backend splits into batches (e.g. 300 items → 3 AI calls). Assume no limits from the user's perspective.
    Manual + AI Manual entry before or after AI Supported

    Eligible fields: short text, long text, number, date, yes/no, multiple-choice. Currently excludes image and signature.

    10.3User journey

    1. Inspector captures onsite notes (voice/text) in journal per item.
    2. After connectivity returns, runs Magic Wand on current item or all forms.
    3. Batch skips requirements without notes.
    4. Inspector reviews filled fields; no AI attribution badges in UI today (will add later).

    10.4Conflict handling

    Field type Target behavior Current state
    Discrete fields Manual values persist unless conflict detected; surface indicator; preserve manual value pending review Batch: intent not to overwrite manual entries. Item-level: may overwrite. Conflict indicator UI to be added.
    Long narrative AI may rewrite or add; not every difference is a hard conflict Partial — no attribution or undo
    All fields Review and edit before publication Supported via form editing

    10.5Offline behavior

    • Magic Wand disabled offline (network required).
    • Manual structured entry remains available offline.
    • Today: cannot start a new inspection and load a checklist while offline. (Future: may allow previously loaded checklists to be opened offline.)

    10.6Performance

    Validate with larger volumes of findings and real inspection data. Current performance acceptable in the demonstrated flow.

    11

    Knowledge Agent (Ask AI)

    11.1Purpose

    Retrieve relevant information from linked documents (e.g. technical reports) and insert into the inspection. Example: identify and state the most relevant clause or condition in concise language.

    11.2User flow

    1. Inspector completes initial observations and manual responses (in journal notes).
    2. Inspector opens Ask AI (host-only; disabled offline).
    3. Inspector selects knowledge agent tied to document set.
    4. Knowledge Agent returns a compiled answer with source document links (not full doc excerpts).
    5. Inspector Insert or Copy — operates on compiled answer, inserted into inspector notes (not form fields directly).
    6. Ask follow up opens nested sheet; session persists until Back to agent picker; Fold returns to notes without losing state.
    7. Inspector may rerun Magic Wand to incorporate inserted reference into narrative fields.

    Non-mock walks use richer Ask AI with doc filters, voice input, chat history, and preview-before-insert dialog.

    11.3Requirements

    • Display compiled response and referenced source documents (links only).
    • Allow insert into inspection (notes today; direct field insert = future enhancement).
    • Preserve original observation when refilling with added context.
    • During re-run of Magic Wand — apply conflict logic when added information contradicts structured answers (target; UI not built).

    11.4Session persistence

    Action Behavior
    Fold / dismiss Ask AI Preserves answer and follow-up trail
    Back to agent selection Clears session
    Reopen Ask AI Restores prior answer or follow-up sheet state (if “Back to agent selection” was not triggered)

    11.5Constraints

    • Image recognition not supported.
    • Performance slower than Magic Wand; optimization needed.
    12

    Review, preview, and report generation

    12.1Pre-publication review

    Before publishing, inspectors must review and manually change entered or AI-generated responses via form and notes editing.

    Publish to workspace path

    Walk Summary reviews items with requirement and form values, assignee, status, location, tags before WIS publish.

    Export path

    Generates report immediately after template selection; no rendered pre-export gate today. (Aim to add a preview step with in-app doc editor, but not in this release.)

    12.2Dual publish paths

    Path Purpose Result
    Export as document default Generate Word/PDF/Excel report file Post-export preview opens
    Publish to project workspace Create/track WIS items in project Walk summary assign/publish flow
    Open decisionDoes Completed require file export, workspace publish, or either? To be clarified.

    12.3Report template selection

    • Chosen at export/publish time, not at inspection create.
    • Team Carbone templates filtered by checklist ID.
    • Default templates (PDF/Excel/Word) from backend when no custom template.
    • Checklist can be linked to multiple template IDs; user can override report template for the same record (e.g. one for external distribution, one for internal circulation).
    • Export regenerates walk summary first to freeze latest form answers.
    • Gap selected template not persisted on inspection metadata after export. (Not sure if this linkage is needed yet.)

    12.4Default report templates

    Required formats when no custom template: Word, PDF, Excel. Default templates should be redesigned to reflect checklist content and polished output (backend/design scope).

    12.5Mobile report preview

    Capability Status
    Preview after export (PDF/Word/Excel) Implemented — download, share, re-open
    Preview before committing export/send Not implemented — gap currently filled by preview / edit of the forms

    Before export or sending, the inspector must be able to verify: responses, project information, preset fields, formatting, signatures. Target = pre-export rendered preview.

    Multi-inspector collaboration

    Direction: Multiple inspectors on same inspection; visibility into who contributed to each requirement.

    Current (unvalidated)

    Single inspector workflow only; no invitation for other inspectors allowed.

    Target (unvalidated) — not this release

    17

    End-to-end onsite day (reference narrative)

    1. Start inspection on phone → pick project + checklist.
    2. Walk site requirement-by-requirement; enter yes/no and photos offline.
    3. Dictate/type notes per item.
    4. Duplicate item when same checklist section / requirement applies again downstream.
    5. Regain signal → batch Magic Wand fills narrative fields from notes.
    6. Open Ask AI on tricky clause → insert compiled answer into notes → rerun wand on item.
    7. Complete signature section(s).
    8. Publish → choose export template → review generated file → share/download.
    9. Optionally track selected findings to project workspace.
    10. Manager finds report under Project → Reports; inspector sees inspection marked Completed.

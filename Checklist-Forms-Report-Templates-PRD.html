    01

    Purpose & product arc

    Billie separates authoring of reusable inspection structure from mapping that structure into customer report documents.

    Layer 1

    Solution Library

    Internal / Solution team

    Regional checklist, form, and report templates that teams can adopt.

    Layer 2

    Team Library

    Customer teams

    Team-owned checklists & forms used on projects; export templates bound to Carbone.

    Layer 3

    Report mapping

    Team (or Solution authors)

    Links checklist/form JSON paths to placeholders in DOCX/XLSX templates.

    Intended customer journey (cross-product)

    1
    Solution authors publish checklist / form / report templates for regions (or Universal).
    2
    A team adopts what they need into their library as a locked, structurally continuous copy (IDs carry over; content is not team-editable — see §8).
    3
    Teams use adopted checklists/forms on projects and map data into report templates for export.
    4
    If a team needs a custom variant, product may later offer an explicit “detach / create editable copy” path; the default adopted asset stays locked to preserve Solution↔report integrity.

    03

    Solution Library

    3.1Design intent

    Solution Library is an internal catalog, not an end-customer workspace. It exists to:

    • Standardize high-quality checklist / form / report starting points across markets.
    • Control distribution via regions (and Universal).
    • Use a real DRAFT → PUBLISHED → ARCHIVED lifecycle so teams only see published assets.
    • Author templates that, once adopted, remain the locked blueprint teams run against.

    Access is gated (email allowlist today; product intent is Solution-team-only).

    3.2Feature descriptions

    Sub-libraryIntentMaturity (web)
    Checklist & Forms templatesStructure + reusable formsFull authoring + publish
    Report templatesDocument layout + mappings + linked checklistFull authoring + publish
    Tag templatesTagging presetsShell / lighter
    Knowledge agent templatesAgent configsShell / lighter

    Regions: UNIVERSAL | AU | US | UK | CA | NZ | HK | SG.

    • Universal = available to all teams.
    • Country-specific templates appear for matching team owner regions (server filters customer catalogs).
    • Authors can multi-select regions when creating templates.

    Checklist template authoring

    1. Create template (name, description, regions).
    2. Edit tree in the shared checklist editor (same UX as team).
    3. Attach forms to requirements; configure section Special fields.
    4. Save draft or Publish.

    Form template authoring

    1. Create named form in Solution Forms catalog (with regions).
    2. Build fields in the form builder (§5).
    3. Publish when ready for teams.

    Report template authoring

    1. Create report template (name, regions).
    2. Open the upload / mapping wizard in Solution mode.
    3. Optionally bind a checklist template + Carbone template id.
    4. Map document tags to JSON paths; embed or link checklist JSON + mappings.
    5. Publish.

    3.3Limitations

    • Tag / Knowledge agent sub-libraries are thinner than Checklist & Report.
    • Teams never edit Solution assets in place; customization belongs on the team side (or future detach).
    • Publish lifecycle is real for Solution; team-side draft/publish is still partially mocked (§4).

    3.4User journey expected

    1. Solution author opens Solution Library → Checklist & Forms (or Reports).
    2. Creates a regional draft, builds checklist/forms/special fields (or report mappings).
    3. Publishes when ready for customer catalogs.
    4. Later, a team adopts the published asset into Team Library as locked and uses it on projects / export.
    04

    Team Checklist & Forms Library

    4.1Design intent

    This is the customer-owned workspace for:

    • Building team-authored checklists and forms (fully editable).
    • Adopting Solution templates into the team library as locked assets for use on projects.
    • Maintaining report/export templates bound to Carbone.
    • Preparing structure for inspections and for the report mapper’s JSON preview.

    Adopted vs authored

    OriginEditability (product intention)Why
    Created in Team LibraryEditableTeam owns the design
    Adopted from Solution LibraryLocked / read-onlyKeeps structure & IDs aligned with Solution-authored report mappings; prevents silent drift
    Implementation noteImplementation note: Locking may not be fully enforced in the UI yet. Treat read-only adopted templates as required product behavior, not optional polish.

    4.2Feature descriptions

    Checklist structure — a checklist is a UIRequirementSet:

    • Ordered checklistItems.ids
    • entities[id] → UIRequirement
    • SECTION: nesting + optional specialFormSchema
    • REQUIREMENT: inspectable leaf + optional formSchema
    • Display numbers for humans; IDs for the machine contract

    Forms on requirements

    • Requirements hold what inspectors fill on mobile (formSchema).
    • Forms library holds named reusable schemas.
    • Authors can: build inline, save to library, or Clone Form from library onto a requirement.
    • Unchanged clone → attach without duplicating the library entry.
    • Edited clone → prompt to save as a new library form.
    • Cloning onto a requirement regenerates form id + field/option ids.

    Team publish / draft (current reality)

    ConceptBackend todayFrontend today
    Checklist statusACTIVE / INACTIVEMock DRAFT / PUBLISHED in localStorage
    Export template statusACTIVE / INACTIVESimilar mock pattern

    Saving a form from the checklist editor may immediately PUT the checklist so form content isn’t stranded in Redux only.

    4.3Limitations

    • Adopted-template lock may not yet disable editors.
    • Team DRAFT/PUBLISHED is UX preview until real lifecycle APIs exist.
    • Homepage “publish” mock does not always write full requirementJson as production would.

    4.4User journey expected

    Team-authored checklist

    1. Team Checklist & Forms → create checklist → build sections/requirements.
    2. Open a requirement → Form builder → add fields / clone from library.
    3. On sections → Special → AI summary / pivots as needed.
    4. Toggle Looped item / Blank after / Notes where export preview needs them.
    5. Save / (mock) publish → use on projects or in report mapper.

    Adopt from Solution

    1. Template library → Use checklist or Adopt form.
    2. Asset appears in team library as locked.
    3. Team uses it on projects / mapping without structural edits.
    4. (Future) Detach only if an editable fork is explicitly required.

    05

    Form building (requirement forms)

    5.1Design intent

    Requirement forms are the inspector input surface: structured answers collected on mobile for each requirement. Authors compose a small, typed field set per requirement so:

    • Inspectors get a clear fill UX.
    • Report export can project answers into Carbone JSON via label slugs.
    • Individual fields can opt into section AI summaries.
    • Forms can be reused via the Forms library without reinventing the schema each time.

    Special outputs (AI summary, pivots) are not requirement form palette items — they live on sections (§6).

    5.2Feature descriptions

    Standard field types

    TypeLabel in UIDescriptionOptions?
    short_textShort textSingle-line answerNo
    long_textLong textMulti-line answerNo
    numberNumberNumeric valueNo
    dateDateCalendar dateNo
    timeTimeTime of dayNo
    multiple_choiceMultiple choicePick one optionYes
    checkboxesCheckboxesPick one or moreYes
    dropdownDropdownSelect from a listYes
    file_uploadFile / imageUpload a file or photoNo
    signatureSignatureSign on screenNo

    Per-field settings (authoring order)

    1. Label — display name; also drives Carbone slug keys in export JSON.
    2. Placeholder — empty-state hint in fill UI.
    3. Smart Description — authoring hint so AI autofill / generation understands the field.
    4. Options — for multiple choice / checkboxes / dropdown (each option has its own id + label).
    5. Required — whether the inspector must answer.
    6. Include in AI summary — toggle + dropdown of parent-section AI summaries by label (see §6).

    Form-level controls

    • Form name — required for saving into the Forms library.
    • Field list: add from palette, reorder (drag), select, remove, clear all.
    • Clone Form from library onto a requirement.
    • Sample answers (formSampleData) and Magic Wand AI fill appear in report-mapper / preview contexts.

    Export relationship

    • Field answers appear under requirement form objects in export JSON keyed by label slug.
    • Pivot header/measure wiring from looped fields is Not in this release (concept only).

    5.3Limitations

    • Smart Description is ahead of full runtime autofill parity in some surfaces.
    • Renaming a label can break existing Carbone tag mappings (slugs, not UUIDs).
    • Cloning onto a requirement always mints new field ids — mappings that keyed by field id must be re-checked.
    • Adopted-locked forms should not open in structural edit mode (enforcement may lag).
    • File / signature preview fidelity in export JSON is sample-oriented.

    5.4User journey expected

    1. Author opens a requirement → Form (or Forms library → edit form).
    2. Adds field types from the left palette until the inspection question is covered.
    3. Sets Label / Placeholder / Smart Description / Options / Required.
    4. Optionally toggles Include in AI summary and picks the section summary by label.
    5. Names the form and saves to library, or keeps it only on this requirement.
    6. Later, in report mapper, sample values / Magic Wand fill blanks for preview mapping.
    06

    Section special fields (AI summary & pivot tables)

    6.1Design intent

    Some outputs span many requirements / findings, not a single inspector fill control. Those belong on the section as specialFormSchema:

    • AI summary — narrative over opted-in nested fields (+ notes), prompted by Smart Description.
    • Pivot tables Not in this release — high-level concept only: tabular aggregates from looped nested findings for report/summary views (single or multi-inspection).

    Putting these on a requirement form would misrepresent ownership and mobile fill UX.

    6.2Feature descriptions

    Entry point

    • On a section row: Special button → SectionSpecialFieldsDialog.
    • Palette includes AI summary for this release.
    • Pivot Table types may appear in authoring UI as future placeholders — Not in this release.

    AI summary block

    ConcernBehavior
    StorageSpecial field on section (type: ai_summary)
    PromptField Smart Description drives the summary instruction
    LabelShown in “Include in AI summary” pickers on nested form fields
    Sources (product model)Opt-in from the source, not only from the summary
    Per-field opt-inOn each standard form field: toggle Include → pick summary by label (includeInAiSummary + aiSummaryId)
    Included sources UISummary settings list linked sources with unlink
    Demo fallbackIf no parent AI summaries exist yet, mock options keep the UI usable

    Pivot tables Not in this release

    High-level concept only: section-level pivot tables would summarize looped findings into a simple table for reports (counts / optional numeric measures). Detailed builder rules, header types, aggregations, and runtime generation are out of scope for this release.

    6.3Limitations

    • Authoring is ahead of full mobile/backend generation for AI summary.
    • Mock AI summary options can appear in demo; real summaries require Special fields saved on the checklist.
    • Pivot tables are Not in this release — concept only.
    • Locked adopted checklists should not allow editing special-field wiring (enforcement may lag).

    6.4User journey expected

    AI summary

    1. Author opens a parent section → Special → add AI summary → set label + Smart Description prompt.
    2. On nested requirements, open forms → for each relevant field, toggle Include in AI summary → pick that summary by label.
    3. Return to Special → confirm Included sources; unlink if needed.
    4. At runtime (future-complete), summary is generated from opted-in answers + notes into report/sp_output.

    Pivot Not in this release

    No shipping user journey this release — concept reserved for a later release.

    07

    Checklist export flags & report JSON preview

    These controls sit beside the form builder: they shape how the checklist appears in export / Carbone sample JSON while authors map report templates. They are primarily preview / mapping aids (with Looped item also feeding pivots).

    7.1Design intent

    Report authors need a realistic JSON tree before documents are wired:

    • Repeating findings (loops),
    • Blank spacer rows,
    • Onsite notes outside the form,
    • Real project metadata instead of placeholders.

    The checklist panel in the upload/export wizard (and team checklist editor flags) lets authors simulate that payload without running a full inspection.

    7.2Feature descriptions

    Checklist bootstrap (mapper panel)

    ControlWhat it does
    From templateGenerate a mock checklist/forms tree from the uploaded DOCX/XLSX (heuristic).
    BlankStart an empty local checklist for manual structure.
    Import library…Clone a team library checklist into the mapper session.

    Per-requirement export flags

    ControlStorageEffect
    Looped itemuiData.loopRequirement (also accepts legacy repeatingFindings / itemizedLoop)Marks requirement as duplicatable findings source. Export preview repeats the finding block ×3 (DEFAULT_REQUIREMENT_LOOP_COUNT). Feeds section pivot header/measure pickers. UI rename of older “Loop ×3”.
    Blank afteruiData.insertBlankAfterInserts a blank notes item (text + photo placeholders) after this requirement in export JSON preview — useful for templates that expect spacer / freeform rows.
    NotescontentSampleData[]Preview-only onsite inspector notes (text + image samples) simulating wis_detail[].content[], separate from form field answers.

    Project sync (JSON preview)

    ControlWhat it does
    Project pickerSelect a real team project for the preview session (JsonPreviewProjectPicker).
    Project & export fieldsSurfaces export_info. and project_info. (name, code, address, client, contacts) plus custom project_info.metadata.* from Project Setup.
    Sync effectSample / Carbone payload project_info (and related metadata) populate from the selected project instead of empty stubs, so tag mapping previews match real report headers.

    Built-in metadata sources include e.g. export_info.templateName, export_info.exportAt, export_info.userName, project_info.name, project_info.projectCode, project_info.clientName, and custom metadata keys.

    JSON preview panel behavior

    • Shows the Carbone-oriented payload used for mapping: conceptually export_info, project_info, wis_detail (requirements / findings / forms / notes), sp_output as needed.
    • Form value keys use label slugs, not field UUIDs.
    • Magic Wand can fill eligible blank form sample fields for denser previews.
    • Path ↔ tag linking uses this JSON tree as the source of truth for mapping.

    7.3Limitations

    • Looped ×3 / Blank after / Notes samples are frontend simulation ahead of full backend parity.
    • Blank checklist bootstrap is disabled in some flows (e.g. when using a report template ID).
    • From-template generation remains heuristic/mock in places.
    • Project sync depends on project APIs / metadata configuration; custom fields only appear if defined on the project.
    • Editing preview sample data does not change production inspection history.

    7.4User journey expected

    1. Open Export / Report Template Mapper → upload or select DOCX/XLSX.
    2. In checklist panel: Import library, From template, or Blank to establish structure.
    3. Mark finding requirements as Looped item; add Blank after where the Word template needs spacer rows.
    4. Open Notes on requirements that should show freeform onsite content in JSON.
    5. Pick a Project so project_info / metadata sync into the JSON preview.
    6. Optionally Magic Wand fill sample form answers.
    7. Bind document tags to JSON paths; save/publish the export template.
    08

    Report template mapping

    8.1Design intent

    Inspection data is structured JSON. Customer reports are DOCX/XLSX with Carbone-style tags. The mapper is the bridge between authoring structure (§4–7) and finished documents.

    8.2Feature descriptions

    1. Upload / select a document template.
    2. Detect tags in the document (and optionally Billie-suggested tags).
    3. Present checklist + form sample data as JSON (§7).
    4. Bind each tag to a JSON path (PathKeyMapping: jsonPath + preview ↔ tagId / tagKey).
    5. Save/publish a team export template (Carbone template id + checklist link + mappings).

    Why checklist IDs matter

    Mappings and special-field configs may reference requirement ids, field ids (pivots, AI targets), and label slugs (Carbone form paths). Adoption must keep the right identifiers continuous (§9).

    Team vs Solution report flows

    ActionBehavior
    Author in SolutionSaves Solution report template (+ optional checklist template id, mappings, checklist JSON)
    Use from Team Template LibraryCreates team export template; if a Solution checklist template is linked, adopt it into the team first
    Publish wizard with Solution checklist idAdopt into team before linking — raw Solution checklist ids must not be stored as team checklist_id

    8.3Limitations

    • Field label renames break slug-based tags even if UUIDs stay stable.
    • Dual adopt paths (client clone vs API) can diverge on nested ID policy (§9).
    • Interactive Word/Excel preview fidelity varies by file complexity.
    • AI auto-draft on template cells is assistive, not a substitute for real inspection data.

    8.4User journey expected

    1. Solution or Team author prepares checklist structure (with loops/notes/specials as needed).
    2. Author opens report mapper, attaches document + checklist JSON preview (with project sync).
    3. Maps tags → paths; validates preview.
    4. Publishes export template for the team (adopting linked Solution checklist when required).
    5. Inspectors run projects; export uses Carbone + mappings against live data shaped like the preview.

    09

    Solution → Team adoption & ID continuity

    9.1Design intent

    Adoption brings a Solution template into the team library as a team-scoped asset that:

    1. Does not mutate the Solution original.
    2. Preserves nested structure and IDs where the adopt contract requires continuity.
    3. Is locked (read-only) for the adopting team — checklist tree, embedded forms, special fields, and adopted form-library entries must not be editable in the team UI.

    Why lock? Solution checklists and report templates are a matched pair. Team-side edits would break Carbone mappings, pivot refs, and AI summary wiring. Regional standardization stays with Solution; teams use the blueprint.

    Adoption is a snapshot, not a live sync. Optional future: Detach / Create editable copy with remapping warnings.

    9.2Feature descriptions

    Form adoption

    • Team Forms → Template Library → Adopt published Solution form → locked team library entry.
    • Optional sourceSolutionFormTemplateId for provenance.
    • Prefer attach-without-structural-edit for locked forms; clone-with-new-ids remains for team-authored library forms.

    Should stay the same: nested UUIDs (intended path), embedded schemas/field ids, labels/structure, loop/special configs. Should change: checklist set id, team form library id, timestamps/team id/status, lock/provenance flags.

    9.3Limitations

    • Locking may not be fully enforced in UI yet.
    • Client clone vs /adopt ID semantics may disagree — product risk for mappings/specials.
    • No re-adopt / “update from Solution” yet.
    • Detach / editable fork not shipped.

    9.4User journey expected

    1. Team opens Template library → Use checklist or Adopt form (or adopts via report “use”).
    2. System creates team-owned row; preserves nested ids on the intended path; sets locked + provenance.
    3. Team runs projects / report mapping against the locked blueprint.
    4. Solution publishes improvements later → team re-adopts or updates via a future explicit flow (not silent overwrite).
    5. Only if customization is required: future Detach → editable copy → remap reports as needed.

    11

    Cross-cutting end-to-end scenarios

    11.1Ship a regional checklist + report

    1. Solution: author checklist template (AU), publish.
    2. Solution: author report template mapped to that checklist’s JSON (loops/notes/project fields as needed), publish.
    3. Team (AU): adopt report from Template Library → system adopts linked checklist into team (locked) → creates team export template.
    4. Team runs inspections → export uses Carbone + mappings against team checklist data.

    11.2Start from Solution checklist only

    1. Team Checklist & Forms → Template library → Use checklist template.
    2. Adopted checklist is locked; nested ids preserved; new checklist set created.
    3. Team uses it on projects / report mapping without editing structure.
    4. (Future) Detach only if a custom fork is explicitly required.

    11.3Build forms + AI summary

    1. Author creates section + nested requirements; builds standard forms (text, choices, number, dates).
    2. Marks finding requirements Looped item where export preview needs repeating findings.
    3. Section → Special → AI summary; fields opt in via Include in AI summary.
    4. In report mapper: import checklist, sync project, preview JSON (×3 loops, notes, blanks), map tags.
    5. Pivot tables: Not in this release — high-level concept only.

    11.4Reuse a Solution form on many requirements

    1. Adopt form into team Forms library as a locked library entry.
    2. Use/attach that form on requirements without opening a structural editor (exact attach UX TBD with lock enforcement).
    3. Labels (and Carbone slugs) stay consistent because the adopted schema is not team-edited.

    Open product decisions / gaps

    1. Enforce locked adopted templates — disable checklist/form/special-field editors; surface lock badge + source template.
    2. Unify checklist adopt paths — client clone vs /adopt ID semantics.
    3. Real team DRAFT/PUBLISHED — replace localStorage mocks.
    4. Field rename policy — Carbone slugs vs UUIDs; migration/versioning.
    5. Re-adopt / update from Solution — define upgrade path when Solution publishes a new version.
    6. Detach / editable fork — optional escape hatch with remapping warnings.
    7. Runtime for AI summary & pivots — authoring ahead of full mobile/backend generation.
    8. Word→checklist extraction — still heuristic/mock in places.
    9. Checkbox explode — ensure export/runtime match pivot preview.
    10. Provenance UX — “Adopted from {Solution template} — locked”.
    11. Export flag backend parity — Looped item / Blank after / Notes samples vs production payload.
    12. Project sync completeness — all custom metadata + offline/empty project states in mapper.
    13

    Success criteria (product)

    • Solution authors can publish regional checklist, form, and report templates without touching customer data.
    • Teams can adopt templates in ≤ a few clicks; adopted assets appear as locked.
    • After checklist adoption (intended path), requirement IDs and embedded form/special field IDs carry over.
    • Form builder exposes the full standard field set with clear settings order and AI-summary opt-in.
    • Special fields remain section outputs; requirement forms remain inspector inputs.
    • Pivot tables remain a high-level concept only — Not in this release.
    • Report mapper JSON preview supports Looped item, Blank after, Notes, and Project sync so authors can map confidently.
    • Team-authored checklists/forms remain fully editable and clearly distinguished from locked adopted ones.

    01

    Purpose & product arc

    Billie separates authoring of reusable inspection structure from mapping that structure into customer report documents, and from filling / generating answers on live inspections.

    Layer 1

    Solution Library

    Internal / Solution team

    Regional checklist, form, and report templates that teams can adopt.

    Layer 2

    Team Library

    Customer teams

    Team-owned checklists & forms used on projects; export templates bound to Carbone.

    Layer 3

    Report mapping

    Team (or Solution when authoring report templates)

    Links checklist/form JSON paths to placeholders in DOCX/XLSX templates.

    Layer 4

    Inspection runtime

    Inspectors (web + mobile)

    Live form answers, AI summaries, photos/notes; export marks completion.

    Intended customer journey (cross-product)

    1
    Solution authors publish checklist / form / report templates for regions (or Universal).
    2
    A team adopts what they need into their library as a locked, structurally continuous copy (IDs carry over; content is not team-editable — see §9).
    3
    Teams use adopted checklists/forms on projects and map data into report templates for export.
    4
    Inspectors fill forms on web/mobile; section AI summaries can be generated on the inspection; checklist edits reflect into open inspections (§15).
    5
    If a team needs a custom variant, product may later offer an explicit “detach / create editable copy” path; the default adopted asset stays locked to preserve Solution↔report integrity.

    03

    Solution Library

    3.1Design intent

    Solution Library is an internal catalog, not an end-customer workspace. It exists to:

    • Standardize high-quality checklist / form / report starting points across markets.
    • Control distribution via regions (and Universal).
    • Use a real DRAFT → PUBLISHED → ARCHIVED lifecycle so teams only see published assets.
    • Author templates that, once adopted, remain the locked blueprint teams run against.
    • Allow Solution authors to remove obsolete templates (including published ones) while making broken report↔checklist links visible.

    Access is gated (email allowlist today; product intent is Solution-team-only).

    3.2Feature descriptions

    Sub-libraryIntentMaturity (web)
    Checklist & Forms templatesStructure + reusable formsFull authoring + publish + delete
    Report templatesDocument layout + mappings + linked checklistFull authoring + publish + delete + Invalid badge
    Tag templatesTagging presetsShell / lighter
    Knowledge agent templatesAgent configsShell / lighter

    Regions: UNIVERSAL | AU | US | UK | CA | NZ | HK | SG.

    • Universal = available to all teams.
    • Country-specific templates appear for matching team owner regions (server filters customer catalogs).
    • Authors can multi-select regions when creating templates.

    Checklist template authoring

    1. Create template (name, description, regions).
    2. Edit tree in the shared checklist editor (same UX as team).
    3. Attach forms to requirements; configure section Special fields.
    4. Save draft or Publish.

    Form template authoring

    1. Create named form in Solution Forms catalog (with regions).
    2. Build fields in the form builder (§5).
    3. Publish when ready for teams.
    4. Delete allowed for any status (including published), same pattern as team forms ⋮ menu.

    Report template authoring

    1. Create report template (name, regions).
    2. Open the upload / mapping wizard in Solution mode.
    3. Optionally bind a checklist template + template ID (UI copy: “Paste your template ID”; not Carbone-branded in the placeholder).
    4. Map document tags to JSON paths; embed or link checklist JSON + mappings.
    5. Publish.

    Delete & link integrity

    ActionBehavior
    Delete checklist (any status, including Published)Card ⋯ → Delete → confirm. If report templates link to it, dialog lists those report names and warns they will no longer be valid.
    Delete report (any status)Card ⋯ → Delete → confirm.
    Invalid badgeReport card whose linkedChecklistTemplateId is set but that checklist is missing from the Solution checklist list.
    Cross-list fetchChecklist and report lists both load when either library is open so Invalid can be computed and delete warnings can name linked reports.

    APIs (mirror form-template delete):

    • DELETE /backoffice/solution-library/checklist-templates/:id
    • DELETE /backoffice/solution-library/report-templates/:id

    Checklist delete invalidates report list caches so Invalid badges refresh.

    3.3Limitations

    • Tag / Knowledge agent sub-libraries are thinner than Checklist & Report.
    • Teams never edit Solution assets in place; customization belongs on the team side (or future detach).
    • Publish lifecycle is real for Solution; team-side draft/publish is still partially mocked (§4).
    • Invalid is client-derived (missing linked checklist id), not a first-class backend status.
    • No dedicated “re-link checklist” repair UX yet — author must edit or delete the orphaned report.
    • Delete depends on backend DELETE support; UI surfaces an error toast if the API rejects.

    3.4User journey expected

    1. Solution author opens Solution Library → Checklist & Forms (or Reports).
    2. Creates a regional draft, builds checklist/forms/special fields (or report mappings).
    3. Publishes when ready for customer catalogs.
    4. Later, a team adopts the published asset into Team Library as locked and uses it on projects / export.
    5. To retire a checklist: ⋯ → Delete → see named linked reports in the confirm dialog → confirm → those report cards show Invalid.
    6. Author deletes or rewires Invalid report templates separately.
    04

    Team Checklist & Forms Library

    4.1Design intent

    This is the customer-owned workspace for:

    • Building team-authored checklists and forms (fully editable).
    • Adopting Solution templates into the team library as locked assets for use on projects.
    • Maintaining report/export templates bound to Carbone.
    • Preparing structure for inspections and for the report mapper’s JSON preview.

    Adopted vs authored

    OriginEditability (product intention)Why
    Created in Team LibraryEditableTeam owns the design
    Adopted from Solution LibraryLocked / read-onlyKeeps structure & IDs aligned with Solution-authored report mappings; prevents silent drift
    Implementation noteImplementation note: Locking may not be fully enforced in the UI yet. Treat read-only adopted templates as required product behavior, not optional polish.

    4.2Feature descriptions

    Checklist structure — a checklist is a UIRequirementSet:

    • Ordered checklistItems.ids
    • entities[id] → UIRequirement
    • SECTION: nesting + optional specialFormSchema
    • REQUIREMENT: inspectable leaf + optional formSchema
    • Display numbers for humans; IDs for the machine contract

    Forms on requirements

    • Requirements hold what inspectors fill on mobile/web (formSchema).
    • Forms library holds named reusable schemas.
    • Authors can: build inline, save to library, or Clone Form from library onto a requirement.
    • Unchanged clone → attach without duplicating the library entry.
    • Edited clone → prompt to save as a new library form.
    • Cloning onto a requirement regenerates form id + field/option ids.

    Team publish / draft (current reality)

    ConceptBackend todayFrontend today
    Checklist statusACTIVE / INACTIVEMock DRAFT / PUBLISHED in localStorage
    Export template statusACTIVE / INACTIVESimilar mock pattern

    Saving a form from the checklist editor may immediately PUT the checklist so form content isn’t stranded in Redux only — and so open inspections can pick up schema / structure changes (§15).

    4.3Limitations

    • Adopted-template lock may not yet disable editors.
    • Team DRAFT/PUBLISHED is UX preview until real lifecycle APIs exist.
    • Homepage “publish” mock does not always write full requirementJson as production would.

    4.4User journey expected

    Team-authored checklist

    1. Team Checklist & Forms → create checklist → build sections/requirements.
    2. Open a requirement → Form builder → add fields / clone from library.
    3. On sections → Special → AI summary as needed.
    4. Toggle Looped item / Blank after / Notes where export preview needs them.
    5. Save / (mock) publish → use on projects, inspections, or report mapper.

    Adopt from Solution

    1. Template library → Use checklist or Adopt form.
    2. Asset appears in team library as locked.
    3. Team uses it on projects / mapping without structural edits.
    4. (Future) Detach only if an editable fork is explicitly required.

    05

    Form building (requirement forms)

    5.1Design intent

    Requirement forms are the inspector input surface: structured answers collected on mobile/web for each requirement. Authors compose a small, typed field set per requirement so:

    • Inspectors get a clear fill UX.
    • Report export can project answers into Carbone JSON via label slugs.
    • Individual fields can opt into one or more section AI summaries.
    • Forms can be reused via the Forms library without reinventing the schema each time.

    Special outputs (AI summary) are not requirement form palette items — they live on sections (§6).

    5.2Feature descriptions

    Standard field types

    TypeLabel in UIDescriptionOptions?
    short_textShort textSingle-line answerNo
    long_textLong textMulti-line answerNo
    numberNumberNumeric valueNo
    dateDateCalendar dateNo
    timeTimeTime of dayNo
    multiple_choiceMultiple choicePick one optionYes
    checkboxesCheckboxesPick one or moreYes
    dropdownDropdownSelect from a listYes
    file_uploadFile / imageUpload a file or photoNo
    signatureSignatureSign on screenNo

    Per-field settings (authoring order)

    1. Label — display name; also drives Carbone slug keys in export JSON.
    2. Placeholder — empty-state hint in fill UI.
    3. Smart Description — authoring hint so AI autofill / generation understands the field.
    4. Smart Description generate — sparkles control drafts a description via POST /form-fields/smart-description (Carbone-shaped single-field document). Result lands in the textarea for edit; not auto-saved. Works for standard fields and AI-summary prompts (typed as Long text for the API).
    5. Options — for multiple choice / checkboxes / dropdown (each option has its own id + label).
    6. Required — whether the inspector must answer.
    7. Include in AI summary — toggle + multi-select of AI summaries by label (includeInAiSummary + aiSummaryIds[]; legacy aiSummaryId = first target for older mobile). See §6.

    Form-level controls

    • Form name — required for saving into the Forms library.
    • Field list: add from palette, reorder (drag), select, remove, clear all.
    • Clone Form from library onto a requirement.
    • Sample answers (formSampleData) and Magic Wand AI fill appear in report-mapper / preview contexts.

    Export / runtime relationship

    • Field answers appear under requirement form objects in export JSON keyed by label slug.
    • In mapper / sample JSON: file_upload → list of https URLs; signature → single URL (or empty when unsigned).
    • On web inspection: file/image fields support upload; signatures remain device-captured (display-only on web when empty).

    5.3Limitations

    • Smart Description generate currently may omit rich context (requirementText / sectionTitle) even though the API supports it; existing text is not sent as a revise prompt (blank → new draft).
    • Renaming a label can break existing Carbone tag mappings (slugs, not UUIDs).
    • Cloning onto a requirement always mints new field ids — mappings that keyed by field id must be re-checked.
    • Adopted-locked forms should not open in structural edit mode (enforcement may lag).
    • Signature capture on web is not supported (mobile captures; web shows existing value).

    5.4User journey expected

    1. Author opens a requirement → Form (or Forms library → edit form).
    2. Adds field types from the left palette until the inspection question is covered.
    3. Sets Label / Placeholder / Smart Description (optionally Generate) / Options / Required.
    4. Optionally toggles Include in AI summary and ticks one or more summaries by label.
    5. Names the form and saves to library, or keeps it only on this requirement.
    6. Later, in report mapper, sample values / Magic Wand fill blanks for preview mapping.
    7. On inspection, inspectors fill fields (including photo upload on web); opted-in answers feed AI summary generate (§15).
    06

    Section special fields (AI summary)

    6.1Design intent

    Some outputs span many requirements / findings, not a single inspector fill control. Those belong on the section as specialFormSchema:

    • AI summary — narrative over opted-in fields across the whole checklist (by summary id), prompted by Smart Description; generatable on the live inspection.

    Putting these on a requirement form would misrepresent ownership and fill UX. Specials materialize as inspection items keyed by the section id so sync stays stable (§15).

    6.2Feature descriptions

    Entry point

    • On a section row: Special button → SectionSpecialFieldsDialog.
    • Palette for this release: AI summary.

    AI summary block

    ConcernBehavior
    StorageSpecial field on section (type: ai_summary)
    PromptField Smart Description drives the summary instruction (supports Smart Description generate)
    LabelShown in “Include in AI summary” pickers
    Sources (product model)Opt-in from the source, not only from the summary
    Per-field opt-inToggle Include → tick one or more summaries (aiSummaryIds[]; legacy aiSummaryId = first)
    Target discoveryAll AI summaries on the checklist (ancestors preferred in ordering); no mock targets
    Included sources UISummary settings list linked sources with unlink (unlink removes that summary id only)
    Contribution scopeWalk-wide by summary field id — not limited to the summary’s section subtree
    RuntimeWeb inspection shows purple AI summary block + Generate → POST /form-fields/summary (§15)

    How specials become inspection items

    • A section with specialFormSchema.fields emits a trailing synthetic item keyed by the section id (stable across re-sync; never duplicated).
    • Live checklist overlays apply the same way as requirement forms.
    • Product contract (e2e): AI special on checklist → inspection shows AI summary + generate control (must not degrade to a plain form).
    • Works for special-only sections (no requirement children) as well as sections that also have requirements.

    Export / Carbone wis_detail shape — after walking a section’s children, if the section has specials, a trailing wis_detail entry is appended that:

    • Has special_form.form, not requirement
    • Does not include requirement-style text / result / notes on that form object
    • Belongs to that section in section (title / path)

    Example (label “Fire safety summary” → slug fire_safety_summary):

    {
  "wis_detail": [
    {
      "section": { "title": "Fire safety", "...": "..." },
      "requirement": {
        "form": { "action_taken": "..." }
      }
    },
    {
      "section": { "title": "Fire safety", "...": "..." },
      "special_form": {
        "form": {
          "fire_safety_summary": ""
        }
      }
    }
  ]
}

    Requirement rows keep requirement.form; the specials row is a sibling entry under the same section. See also §7 JSON preview.

    6.3Limitations

    • Cross-section AI targeting is powerful but easy to misconfigure (any field can point at any summary id).
    • Requirement-level uiData multi-target exists in the model; primary authoring path is per-field.
    • Locked adopted checklists should not allow editing special-field wiring (enforcement may lag).
    • Without any authored AI summary, Include controls have no real targets (mocks removed by design).

    6.4User journey expected

    AI summary

    1. Author opens a section → Special → add AI summary → set label + Smart Description (optionally Generate).
    2. On requirements, open forms → for each relevant field, toggle Include in AI summary → tick one or more summaries.
    3. Return to Special → confirm Included sources; unlink if needed.
    4. Create/open inspection → special item appears for the section → fill opted-in fields → Generate AI summary → edit → autosave.
    5. Export / report mapping can consume stored summary text / specials.* paths.

    07

    Checklist export flags & report JSON preview

    These controls sit beside the form builder: they shape how the checklist appears in export / Carbone sample JSON while authors map report templates. They are primarily preview / mapping aids (Looped item is a preview / mapping aid).

    7.1Design intent

    Report authors need a realistic JSON tree before documents are wired:

    • Repeating findings (loops),
    • Blank spacer rows,
    • Onsite notes outside the form,
    • Section specials (AI summary placeholders),
    • Media fields as URL shapes matching runtime,
    • Real project metadata instead of placeholders.

    The checklist panel in the upload/export wizard (and team checklist editor flags) lets authors simulate that payload without running a full inspection.

    7.2Feature descriptions

    Checklist bootstrap (mapper panel)

    ControlWhat it does
    From templateGenerate a mock checklist/forms tree from the uploaded DOCX/XLSX (heuristic).
    BlankStart an empty local checklist for manual structure.
    Import library…Clone a team library checklist into the mapper session.

    Per-requirement export flags

    ControlStorageEffect
    Looped itemuiData.loopRequirement (also accepts legacy repeatingFindings / itemizedLoop)Marks requirement as duplicatable findings source. Export preview repeats the finding block ×3 (DEFAULT_REQUIREMENT_LOOP_COUNT). UI rename of older “Loop ×3”.
    Blank afteruiData.insertBlankAfterInserts a blank notes item (text + photo placeholders) after this requirement in export JSON preview — useful for templates that expect spacer / freeform rows.
    NotescontentSampleData[]Preview-only onsite inspector notes (text + image samples) simulating wis_detail[].content[], separate from form field answers.

    Project sync (JSON preview)

    ControlWhat it does
    Project pickerSelect a real team project for the preview session (JsonPreviewProjectPicker).
    Project & export fieldsSurfaces export_info. and project_info. (name, code, address, client, contacts) plus custom project_info.metadata.* from Project Setup.
    Sync effectSample / Carbone payload project_info (and related metadata) populate from the selected project instead of empty stubs, so tag mapping previews match real report headers.
    Project Setup integritySaving project details + report metadata must run sequentially (updateProject then updateReportMetadata) so parallel saves cannot wipe custom metadata.

    Built-in metadata sources include e.g. export_info.templateName, export_info.exportAt, export_info.userName, project_info.name, project_info.projectCode, project_info.clientName, and custom metadata keys.

    JSON preview panel behavior

    • Shows the Carbone-oriented payload used for mapping: conceptually export_info, project_info, wis_detail (requirements / findings / forms / notes / trailing specials), sp_output as needed.
    • Form value keys use label slugs, not field UUIDs.
    • Media samples: file/image → URL list; signature → single URL.
    • Magic Wand can fill eligible blank form sample fields for denser previews.
    • Path ↔ tag linking uses this JSON tree as the source of truth for mapping.
    • Template ID pane placeholder: “Paste your template ID” (shared team + Solution editors).

    Trailing special_form in wis_detail

    After a section’s requirement children are emitted, if that section has specials, the preview / export payload appends a trailing wis_detail row (§6):

    • Uses special_form.form (slug keys for AI summary fields) — not a requirement object
    • Omits requirement-style text / result / notes on that form object
    • Carries the same section title/path as sibling requirement rows
    • Emitted even for special-only sections (no requirement children)

    Mappers should bind special outputs via paths like wis_detail[].special_form.form.{labelSlug} (and related specials.* helpers where present), not via requirement.form.

    7.3Limitations

    • Looped ×3 / Blank after / Notes samples are frontend simulation ahead of full backend parity.
    • Blank checklist bootstrap is disabled in some flows (e.g. when using a report template ID).
    • From-template generation remains heuristic/mock in places.
    • Project sync depends on project APIs / metadata configuration; custom fields only appear if defined on the project.
    • Editing preview sample data does not change production inspection history.

    7.4User journey expected

    1. Open Export / Report Template Mapper → upload or select DOCX/XLSX (or paste template ID).
    2. In checklist panel: Import library, From template, or Blank to establish structure.
    3. Mark finding requirements as Looped item; add Blank after where the Word template needs spacer rows.
    4. Open Notes on requirements that should show freeform onsite content in JSON.
    5. Ensure section specials exist if mapping ….specials.… paths.
    6. Pick a Project so project_info / metadata sync into the JSON preview.
    7. Optionally Magic Wand fill sample form answers.
    8. Bind document tags to JSON paths; save/publish the export template.
    08

    Report template mapping

    8.1Design intent

    Inspection data is structured JSON. Customer reports are DOCX/XLSX with Carbone-style tags. The mapper is the bridge between authoring structure (§4–7) and finished documents — and the same shapes should match what inspections emit at export time (§15).

    8.2Feature descriptions

    1. Upload / select a document template or load by template ID.
    2. Detect tags in the document (and optionally Billie-suggested tags).
    3. Present checklist + form sample data as JSON (§7), including specials and media URL shapes.
    4. Bind each tag to a JSON path (PathKeyMapping: jsonPath + preview ↔ tagId / tagKey).
    5. Save/publish a team export template (template id + checklist link + mappings).

    Why checklist IDs matter

    Mappings and special-field configs may reference requirement ids, field ids (AI targets / aiSummaryIds), and label slugs (Carbone form paths). Adoption must keep the right identifiers continuous (§9).

    Team vs Solution report flows

    ActionBehavior
    Author in SolutionSaves Solution report template (+ optional checklist template id, mappings, checklist JSON)
    Use from Team Template LibraryCreates team export template; if a Solution checklist template is linked, adopt it into the team first
    Publish wizard with Solution checklist idAdopt into team before linking — raw Solution checklist ids must not be stored as team checklist_id

    8.3Limitations

    • Field label renames break slug-based tags even if UUIDs stay stable.
    • Dual adopt paths (client clone vs API) can diverge on nested ID policy (§9).
    • Interactive Word/Excel preview fidelity varies by file complexity.
    • AI auto-draft on template cells is assistive, not a substitute for real inspection data.
    • Solution report cards may show Invalid if their linked checklist was deleted (§3).

    8.4User journey expected

    1. Solution or Team author prepares checklist structure (with loops/notes/specials as needed).
    2. Author opens report mapper, attaches document + checklist JSON preview (with project sync).
    3. Maps tags → paths (including form slugs and specials.*); validates preview.
    4. Publishes export template for the team (adopting linked Solution checklist when required).
    5. Inspectors run projects; Export as Document uses Carbone + mappings; successful export contributes to Completed lifecycle (§15).

    09

    Solution → Team adoption & ID continuity

    9.1Design intent

    Adoption brings a Solution template into the team library as a team-scoped asset that:

    1. Does not mutate the Solution original.
    2. Preserves nested structure and IDs where the adopt contract requires continuity.
    3. Is locked (read-only) for the adopting team — checklist tree, embedded forms, special fields, and adopted form-library entries must not be editable in the team UI.

    Why lock? Solution checklists and report templates are a matched pair. Team-side edits would break Carbone mappings and AI summary wiring. Regional standardization stays with Solution; teams use the blueprint.

    Adoption is a snapshot, not a live sync. Optional future: Detach / Create editable copy with remapping warnings.

    Form adoption

    9.3Limitations

    • Locking may not be fully enforced in UI yet.
    • Client clone vs /adopt ID semantics may disagree — product risk for mappings/specials.
    • No re-adopt / “update from Solution” yet.
    • Detach / editable fork not shipped.

    9.4User journey expected

    1. Team opens Template library → Use checklist or Adopt form (or adopts via report “use”).
    2. System creates team-owned row; preserves nested ids on the intended path; sets locked + provenance.
    3. Team runs projects / report mapping against the locked blueprint.
    4. Solution publishes improvements later → team re-adopts or updates via a future explicit flow (not silent overwrite).
    5. Only if customization is required: future Detach → editable copy → remap reports as needed.

    11

    Cross-cutting end-to-end scenarios

    11.1Ship a regional checklist + report

    1. Solution: author checklist template (AU), publish.
    2. Solution: author report template mapped to that checklist’s JSON (loops/notes/specials/project fields as needed), publish.
    3. Team (AU): adopt report from Template Library → system adopts linked checklist into team (locked) → creates team export template.
    4. Team runs inspections → export uses Carbone + mappings against team checklist data → inspection moves to Completed.

    11.2Start from Solution checklist only

    1. Team Checklist & Forms → Template library → Use checklist template.
    2. Adopted checklist is locked; nested ids preserved; new checklist set created.
    3. Team uses it on projects / report mapping without editing structure.
    4. (Future) Detach only if a custom fork is explicitly required.

    11.3Build forms + AI summary + inspect

    1. Author creates section + nested requirements; builds standard forms (text, choices, number, dates, file).
    2. Marks finding requirements Looped item.
    3. Section → Special → AI summary; fields multi-opt-in via Include in AI summary.
    4. In report mapper: import checklist, sync project, preview JSON (×3 loops, notes, blanks, specials.*, media URLs), map tags.
    5. Create inspection → fill fields / upload photos → Generate AI summary on the special item → Export as Document → Completed.

    11.4Reuse a Solution form on many requirements

    1. Adopt form into team Forms library as a locked library entry.
    2. Use/attach that form on requirements without opening a structural editor (exact attach UX TBD with lock enforcement).
    3. Labels (and Carbone slugs) stay consistent because the adopted schema is not team-edited.

    11.5Retire a Solution checklist linked to reports

    1. Solution Library → Checklist card ⋯ → Delete.
    2. Confirm dialog lists linked report template names and warns they become invalid.
    3. Report library shows Invalid on those cards until deleted or rewired.

    11.6Checklist edit after inspection exists

    1. Create inspection from a checklist.
    2. Edit the checklist (add field / add requirement) and save/publish.
    3. Reopen inspection: new fields appear via live schema overlay; new items appear via server structure sync (Syncing… → Synced).

    15

    Inspection runtime (web) — reflection, AI summary, collab, lifecycle

    Added since the original authoring/mapping-focused draft. This is where checklist/forms/report contracts meet live work.

    15.1Design intent

    • Checklist remains the source of truth for field schemas on open inspections.
    • New requirements are added by ms-walk server structure sync after checklist save — not by a second client writer (client-side structure sync on open was removed to avoid double-append).
    • Section specials appear as real inspection items; AI summaries are generatable and editable on web.
    • Collaborative hosts/attendees see form answers update live.
    • Exporting a report is a primary path to mark an inspection completed (aligned with mobile).

    15.2Feature descriptions

    Checklist ↔ inspection reflection

    ConcernBehavior
    Live form schemasOverlay live checklist formSchema / special schemas onto issue snapshots when fetching checklist (refetch threshold ~30s)
    New itemsServer sweep after checklist save; structureSyncStatus: SYNCING / SYNCED / null — badges on journal list + detail
    SpecialsTrailing item per section with specials; keyed by section id (§6)
    Contract (e2e)Edit form after inspection exists → new field appears; add requirement → item count grows via sweep (may take tens of seconds)

    On-form AI summary

    ConcernBehavior
    UIPurple AI summary block + sparkles Generate
    CollectWalk-wide opted-in fields via includeInAiSummary + aiSummaryTargets → POST /form-fields/summary (Smart Description as note)
    BlanksBlank answers still sent; AI may account for them
    PersistEditable long text; autosave like other fields
    Empty sourcesInfo toast directing authors to opt fields in from the checklist builder

    Web form fill

    ConcernBehavior
    Photo / fileUpload for file/image fields; URL thumbnails
    SignatureDisplay existing; “captured on mobile” when empty — no web draw/upload
    AutosaveDebounced (~1s); clear saved / progress affordances

    Ask image → draft note (adjacent)

    • Sparkles on journal image → POST …/ai/image/read → local draft text message for review before Submit.
    • Feeds the notes stream that can later inform autofill / summaries / export content.

    Collaborative live form answers

    ConcernBehavior
    Socket payloadsW12/W24 may carry formAnswers; apply with freshness (updatedAt); empty object clears; null/absent leaves cache
    New issuesSocket-created issues seed containers so attendees can post immediately
    ScopeViewing-path scoped so other walks don’t pollute the open journal

    Lifecycle / Completed

    Derived status includes: archived → completed; all items published → completed; extraData.lifecycle === "completed" → completed; else scheduled / in progress.
    Export as Document → Export Complete contributes to Completed (e2e-covered).

    15.3Limitations

    • Structure sync depends on ms-walk deploy and correct team/checklist resolution for invited users.
    • Live overlay updates schemas; brand-new items wait on server sweep.
    • Signature capture remains mobile-first.
    • Completing via export is one lifecycle path; not every publish path may set the same flag.

    15.4User journey expected

    1. Create inspection from a checklist that includes forms + section AI summary.
    2. Fill opted-in fields (upload photos on web where needed); optionally Ask image → draft note → Submit.
    3. Open the section special item → Generate AI summary → edit → wait for Saved.
    4. Host edits while attendee views → attendee sees form answers update without refresh.
    5. Author adds a field/requirement on the checklist and saves → inspection reflects (fields live; items via Syncing…).
    6. Publish items as needed → Export as Document with mapped template → inspection appears under Completed.
